# Database Migration Rules

Rules for writing and reviewing database schema migrations. Apply these when creating, modifying, or reviewing migration files.

## File Naming

- Use timestamp-based filenames: `YYYYMMDDHHMMSS_<slug>.sql`.
- Generate with the project's migration script, never by hand-picking a number.
- Slug: lowercase, underscores only, descriptive (`add_skills_catalog`, `add_content_url_to_skills`).
- Never rename or edit a migration that has already been applied to any environment.

## Structure

Every migration must have:

```sql
-- +goose Up
-- <slug> — <engine (PostgreSQL|SQLite)>
-- <one-line description of what this does and why>

<Up DDL here>

-- +goose Down
<Down DDL here — exact reverse of Up>
```

No orphaned Up without a Down. The Down must actually reverse the Up — not a comment, not empty.

## Backward Compatibility (Expand-Contract)

The previously-deployed binary must still work after the migration runs. This means:

**Never in a single migration:**
- Add a NOT NULL column without a DEFAULT (old binary can't insert rows)
- Drop a column the old binary still reads or writes
- Rename a column or table the old binary references
- Change a column type in a breaking way (e.g., TEXT → UUID)
- Add a UNIQUE or CHECK constraint that existing rows violate

**Instead, use expand-contract across two releases:**

1. **Release N** (expand): Add new column with DEFAULT, or add new table. Old and new binary both work.
2. **Release N+1** (contract): Remove the old column/table once no code references it.

## Indexes

- Add indexes before merging. A missing index on a column used in WHERE/ORDER BY is a review reject.
- Large tables: use `CREATE INDEX CONCURRENTLY` to avoid table locks.
  - Add `-- +goose NO TRANSACTION` at the top of the migration (CONCURRENTLY can't run in a transaction).
- Name indexes explicitly: `idx_<table>_<columns>` (e.g., `idx_skills_catalog_status`).
- Foreign key columns always need an index on the referencing side.

## Special Cases

**Enum types (Postgres):** `ALTER TYPE … ADD VALUE` cannot run in a transaction.
Add `-- +goose NO TRANSACTION` at the top.

**IF NOT EXISTS:** Only permitted in the baseline migration (migration 00001 or equivalent).
All subsequent migrations must be idempotent through proper Up/Down, not through `IF NOT EXISTS`.

**Data migrations:** Keep data migrations separate from schema migrations.
A migration that changes schema should not also backfill data in the same file.

## MinSchemaVersion

If new application code reads a newly added column, bump `MinSchemaVersion` to this migration's timestamp in the same commit. This prevents the new binary from starting against an old schema.

## Review Checklist

Before merging a migration:

- [ ] Generated by the migration script (correct timestamp, no hand-picked number)
- [ ] Has both `-- +goose Up` and `-- +goose Down`
- [ ] Down exactly reverses Up
- [ ] Old binary still works after Up runs (expand-contract respected)
- [ ] All new columns used in WHERE/ORDER BY have indexes
- [ ] `-- +goose NO TRANSACTION` present if using `CONCURRENTLY` or `ALTER TYPE ADD VALUE`
- [ ] No `IF NOT EXISTS` (unless this is the baseline)
- [ ] `MinSchemaVersion` bumped if new code reads new column
- [ ] `bash scripts/pr-checks/check-migration-versions.sh` prints OK
